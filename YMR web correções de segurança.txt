1. JWT Tokens — Migrar para httpOnly Cookies

  Problema: Tokens no localStorage são lidos por qualquer JavaScript na página. 
  Solução — Backend deve mudar o fluxo de auth:

  ┌─────────────────────────────────────────────────────┐
  │ ATUAL (inseguro)                                     │
  │                                                      │
  │ POST /auth/login  →  { access_token: "eyJ..." }      │
  │ Frontend salva em localStorage                        │
  │ Frontend envia: Authorization: Bearer <token>         │
  └─────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────┐
  │ CORRETO (seguro)                                     │
  │                                                      │
  │ POST /auth/login  →  Define Cookie httpOnly,Secure    │
  │ Frontend NAO recebe o token                           │
  │ Cookie é enviado automaticamente pelo browser          │
  │ Frontend NAO pode ler o token (document.cookie = "")  │
  └─────────────────────────────────────────────────────┘

  // apiFetch — não precisa mais injetar Authorization
  // Cookies httpOnly são enviados automaticamente pelo browser
  // MAS precisa de credentials: 'include'
  const res = await fetch(url, {
    ...init,
    credentials: 'include',  // Envia cookies httpOnly
  });

  ▎ Nota: Remova também o localStorage.removeItem('ymr_access_token') do
  logout(). O logout passa a ser POST /auth/logout que limpa o cookie no
  backend.

2. CSRF Protection

  Problema: Como cookies são enviados automaticamente, um site malicioso pode
  fazer requests autenticados no nome do usuário.

  Solução — Double Submit Cookie Pattern:

  // Backend — Ao criar a sessão, gera também um CSRF token
  // Logout — limpa AMBOS os cookies

  ▎ Alternativa mais simples: Se o backend usar sameSite: 'strict' nos cookies,
  CSRF já é mitigado (o cookie não é enviado cross-site). Mas o middleware de
  validação é a defesa em profundidade.

3. Sanitização de HTML (Stored XSS)

  Problema: O backend aceita HTML de admins e devolve sem limpar. Se a conta de
  admin for comprometida, o atacante injeta <script> em posts/produtos.

  Solução — Sanitizar no BACKEND antes de salvar (e no frontend como defesa
  extra):

  // Backend — sanitizar antes de salvar no banco
 
  ▎ Por quê sanitizar no backend? Porque o frontend já sanitiza com DOMPurify,
  mas se o atacante enviar requests diretamente à API (bypass do frontend), o
  HTML malicioso seria salvo no banco. Sanitizar em AMBOS os lados = defesa em
  profundidade.

5. Política de Passwords

  Problema: 6 caracteres é insuficiente. A validação é só no frontend.

  // Backend — validar no registro e na troca de senha
  function validatePassword(password: string): string | null {
    if (password.length < 8)
      return 'Password must be at least 8 characters.';
    if (password.length > 128)
      return 'Password must be less than 128 characters.';
    if (!/[A-Z]/.test(password) || !/[a-z]/.test(password))
      return 'Password must contain uppercase and lowercase letters.';
    if (!/[0-9]/.test(password))
      return 'Password must contain at least one number.';
    return null;
  }

6. Token Refresh (Refresh Token Rotation)

  Problema: Access token expira em 15 min e o usuário é desconectado sem
  refresh.

  Fluxo correto:

  ┌──────────────────────────────────────────────────────────┐
  │ 1. LOGIN                                                 │
  │    Backend gera:                                          │
  │    - Access Token  (expires: 15min)  → Cookie httpOnly     │
  │    - Refresh Token (expires: 7 dias) → Cookie httpOnly     │
  │                                                          │
  │ 2. REQUEST NORMAL (dentro de 15min)                       │
  │    Frontend faz request → cookie enviado automaticamente   │
  │    Backend valida access token → OK                       │
  │                                                          │
  │ 3. ACCESS TOKEN EXPIRADO (após 15min)                     │
  │    Frontend recebe 401 → automaticamente chama /refresh    │
  │    Backend valida refresh token → gera NOVO par           │
  │    → Novo Access Token (15 min) + Novo Refresh Token (7d) │
  │                                                          │
  │ 4. REFRESH TOKEN USADO (one-time rotation)                │
  │    Cada refresh invalida o token anterior                  │
  │    Se alguém tentar usar o token antigo → DETECTAR ROUBO  │
  └──────────────────────────────────────────────────────────┘

  // Login — gera ambos os tokens
